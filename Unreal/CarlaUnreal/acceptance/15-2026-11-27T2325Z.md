## Problems found (adversarial)

### B1 — the gate is not "the map the run started in": it is sticky for the whole process, and the documents/log say otherwise

Reproduction (verbatim, 3 minutes):

1. `UnrealEditor.exe C:\GameProject\CarlaUE5\carla\Unreal\CarlaUnreal\CarlaUnreal.uproject -game -windowed /Game/Carla/Maps/Town05_Opt -ExecCmds="TestPlatform.BackendAutoStart 0"`
2. wait for the log line `map /Game/Carla/Maps/Town05_Opt: config panel disabled (not an entry map)`
3. `C:\SoftWare\MiniConda\envs\chat_carla\python.exe -c "import carla;c=carla.Client('127.0.0.1',2000);c.set_timeout(120);c.load_world('L_TestPlatformEntry')"`
4. observe the log

Observed (run H, `evidence-15/gate-and-error-excerpts.txt`):

```
LogTestPlatform: map /Game/Carla/Maps/Town05_Opt: config panel disabled (not an entry map)
LogWorld: Bringing World /Game/TestPlatform/Maps/L_TestPlatformEntry.L_TestPlatformEntry up for play … 07.24.10
LogTestPlatform: map /Game/TestPlatform/Maps/L_TestPlatformEntry: config panel enabled (entry map)
LogTestPlatform: test platform UI added to the game viewport
```

and after one more load (run I, which **started on Town05** at 07:23:40):

```
LogTestPlatform: map /Game/Carla/Maps/L_TestPlatformEntry: config panel enabled (entry map)
LogTestPlatform: map /Game/Carla/Maps/Town10HD_Opt: config panel enabled (this run started on an entry map)
```

`Private/TestPlatformModule.cpp:748` is `bEntryMapArmed = bEntryMapArmed || bOnEntryMap;` and nothing ever
resets `bEntryMapArmed` (grep: it is only written there, read at 749/756). So the implemented rule is
"allow forever once any world in this process was an entry map", not "the map the run started in".

Why it fails:

- `Platform/docs/architecture.md` §9.1 states (single bullet, verbatim):

  ```
  闸门按"本次运行从哪张图启动"闩锁，不是"当前地图"：… 所以进程第一次看到白名单里的地图就记下"这是一次配置界面运行"，之后一直允许；从别的图启动的进程永远不允许。
  ```

  Run H/I contradict the final clause ("从别的图启动的进程永远不允许"); the commit message repeats the
  same claim ("闸门按『本次运行从哪张图启动』闩锁").
- The audit line the same section tells operators to trust, `map <pkg>: config panel enabled|disabled (<原因>)`,
  prints the factually wrong reason `this run started on an entry map` for a run that started on Town05 (run I).
- Consequence in the editor/PIE workflow (inferred from the same process-scoped state, **not executed** —
  PIE is barred in this review): `EditorStartupMap` is the entry level and the engine's base config sets
  `LoadLevelAtStartup=ProjectDefault`, so the editor opens the entry level; the module instance lives for the
  whole editor process and `TickRuntime` skips only `EWorldType::Editor` — so one PIE run from the entry
  level arms the panel for the rest of that editor session, and a later PIE from Town05/Town10HD will show
  the config panel again. That is the user's original complaint reappearing inside one editor session;
  the documents promise it cannot happen. (The editor's own `LastLevel` is
  `/Game/Carla/Maps/Town10HD_Opt`; with `LoadLevelAtStartup=LastOpened` the editor would not even open the
  entry level — it uses `ProjectDefault` here.)

### B2 — the shipped default start path logs CARLA **Errors** on every launch

Reproduction: `UnrealEditor.exe …CarlaUnreal.uproject -game` (no map argument), then
`Select-String -Path Unreal/CarlaUnreal/Saved/Logs/CarlaUnreal.log -Pattern 'LogCarla: Error'`.

Observed (runs A, B, D, H):

```
LogCarla: Error: No OpenDrive file found for map 'L_TestPlatformEntry'
LogCarla: Error: Invalid Map
```

and the backend's own stderr when it connects to that entry level (`15-backend-stderr-errors.txt`):

```
ERROR: unable to parse the OpenDRIVE XML string
ERROR: unable to parse the OpenDRIVE XML string
```

Why it fails: the deliverable makes an OpenDrive-less level the normal starting point and fixes only the
Python side (`session_runner.py` catches `RuntimeError` from `world.get_map()`), but the engine side still
reports the normal state as two Errors and the panel's backend window shows `ERROR:` lines on a healthy
run. The acceptance L1 rule "no Error/Fatal logs" is not met, and an operator reading the backend window
sees an error story that contradicts the documented "empty shell is expected".

### B3 — `run-editor-lowquality.ps1 -Map <any non-entry map>` can never report success

Reproduction: `pwsh -File Unreal/CarlaUnreal/Source/TestPlatform/Platform/tools/run-editor-lowquality.ps1 -Map /Game/Carla/Maps/Town05_Opt`.

Observed (code, lines 134–158, combined with run C's log): the script waits up to 8 minutes for
`Select-String -Pattern 'test platform UI added'` in `CarlaUnreal.log`. By design that marker **cannot**
appear on a non-entry map (run C: no `test platform UI added`, only
`config panel disabled (not an entry map)`), so the script always ends with
`the UI marker never appeared - check <logs>` in red, although the map loaded and the run is exactly the
documented "browse a town, no panel" behaviour. The same commit's header comment advertises that usage.
(Not executed end-to-end here — it would sit for 8 minutes and start its own backend window; the failure
path is deterministic from the script and the measured log.)
