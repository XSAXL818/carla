## Problems found (adversarial)

### D1 — BLOCKING. The engine-side 15 s "no tick cue" watchdog ejects a **live** client from synchronous mode without telling it, and in this product that kills the running session.

What changed (`Plugins/Carla/Source/Carla/Game/CarlaEngine.cpp:946-973`): a wall-clock watchdog inside the per-frame synchronous wait loop
`do { Server.RunSome(1u); … } while (bSynchronousMode && !Server.TickCueReceived());`
- `RunSome(1u)` is `SyncRunFor(1 ms)` (`Plugins/Carla/Source/Carla/Server/CarlaServer.cpp:4116-4119`), so the loop really spins and the check does execute.
- Gate: `bSynchronousMode && (FPlatformTime::Seconds() - SyncWaitStarted) > 15.0`. `SyncWaitStarted` is re-taken at the top of every frame's wait, so it fires whenever one wait exceeds 15 s.
- On expiry it sets `CurrentSettings.bSynchronousMode = false`, `CurrentSettings.FixedDeltaSeconds.Reset()`, `bSynchronousMode = false`, `Server.GetStreamingServer().SetSynchronousMode(false)`, `CurrentEpisode->ApplySettings(CurrentSettings)` — the last call re-enters `FCarlaEngine::OnEpisodeSettingsChanged` (`:1440-1459`), which also calls `FCarlaEngine_SetFixedDeltaSeconds({})`, i.e. `FApp::SetBenchmarking(false)`, `SetFixedDeltaTime(0)`.
- There is **no** cvar, no opt-out, and no client-connection test. It applies to every synchronous client of this CARLA fork, not just the test platform. (The primary `carla::rpc::Server` exposes no client count — only `SecondaryServer`/`StreamingServer` have `HasClientsConnected()` — so "no client" is not directly available; that is the real gap the change worked around.)

Observed, two independent ways:

1. **A deliberately slow but alive client** (`08-sync-pause-probe.log`, script connects to the editor's own server on 2000, sets `synchronous_mode=True, fixed_delta_seconds=0.05`, ticks once, then pauses 22 s — the "heavy agent step / debugger pause" case):
   ```
   settings after apply: True 0.05
   ticked once, frame = 6876
   {"t": 14.1, "frame": 6876, "sync": true,  "fixed_delta": 0.05}
   {"t": 16.1, "frame": 6934, "sync": false, "fixed_delta": null}
   {"t": 22.1, "frame": 7256, "sync": false, "fixed_delta": null}
   frame delta over the 22 s pause: 380
   ```
   Editor log: `LogCarla: Warning: No tick cue for 15 s in synchronous mode (client gone?); switching back to asynchronous so the game thread keeps running`.
   The client was alive the whole time and lost its synchronous mode **silently**: 380 frames ran behind its back and `fixed_delta_seconds` became `None`.

2. **In-product reproduction** (Run B3; the panel's own auto-started preview session at 20 Hz, backend alive): I suspended the live `python run.py` (pid 39712) for 22 s with `NtSuspendProcess`, then resumed it.
   - `editorResponding`: False at t=0…13.1, **True from t=15.1** → the watchdog fired and un-froze the game thread.
   - Editor log: the same `No tick cue for 15 s …` warning.
   - `GET /sessions/current` after resume:
     `"state":"error","error":"tick 失败：unsupported operand type(s) for +=: 'float' and 'NoneType'","tick":250,"sim_time":83.0,…,"events":1`
   - Panel screenshot `10-session-error-after-15s-fallback.png`: chip `会话 · 错误`, engine chip still claims `同步模式 · 20 Hz`.
   - Cause: the backend reads the fixed delta on every tick (`Source/TestPlatform/Platform/backend/app/session_runner.py:712`, `self.sim_time += self.world.get_settings().fixed_delta_seconds`) and its loop `break`s on any exception (`:726-731`). The watchdog reset that value to `None`; before this commit a 22 s stall simply paused the session and it resumed.

Reproduction (verbatim, from a clean start):
1. Nothing on 8765: `Get-CimInstance Win32_Process -Filter "Name='python.exe'"` → none; `Get-NetTCPConnection -State Listen -LocalPort 8765` → none.
2. `G:\Epic\EpicApps\UE_5.8_Carla\Engine\Binaries\Win64\UnrealEditor.exe "C:\GameProject\CarlaUE5\carla\Unreal\CarlaUnreal\CarlaUnreal.uproject" -game -windowed -ResX=1600 -ResY=900 -nosound -nologtimes -TestPlatformBackend=http://127.0.0.1:8765`
3. Wait for the panel's preview session (`GET http://127.0.0.1:8765/sessions/current` → `"state":"preview"`, `"sim_time"` increasing).
4. Suspend the backend's python process for 22 s (e.g. `NtSuspendProcess`, then `NtResumeProcess`).
5. Within ~15 s the editor log gains `LogCarla: Warning: No tick cue for 15 s in synchronous mode (client gone?); …`.
6. After the resume, `GET /sessions/current` → `"state":"error","error":"tick 失败：unsupported operand type(s) for +=: 'float' and 'NoneType'"`; the panel shows `会话 · 错误`.

Why this fails acceptance: the acceptance brief asks explicitly whether the change "alter[s] legitimate synchronous-stepping semantics (e.g. a live client that intentionally pauses between ticks, determinism, recordings sampled at fixed deltas)". It does — measured, not hypothetical — and the consequence inside this very product is a dead session rather than a pause. It also **masks a client-side wedge**: before the change the hang was the only signal that the client stopped driving the clock; now the same condition is a single `Warning` and the world silently runs free, which for a recorder sampled at fixed deltas means the remainder of the recording is no longer at fixed deltas (the setting is cleared) and the client's own clock bookkeeping (`session_runner.py:712`) breaks. `FPlatformTime::Seconds()` is wall clock, so an unrelated 15 s game-thread stall (OS pause, GPU hitch) triggers the same thing. It cannot mask a *server-side* deadlock elsewhere on the game thread, and it does not fix one — it only stops this particular spin from blocking the editor.

Trade-off, stated fairly: the change is **needed** for the user's requirement — the panel auto-starts a synchronised preview, so closing the backend window froze the whole editor before this commit (I reproduced the freeze: `editorResponding=False` until the watchdog fired, then recovery, `06-after-window-close.png`). The direction is right; the implementation is not acceptable as shipped, because it is global, unconditional, unconfigurable and silent. Defensible shape: a timeout cvar (0 = wait forever) or a test-platform-scoped gate, plus, preferably, gating on "no client connected" (which needs the rpc::Server to expose its session count), plus making the backend tolerate a lost synchronous mode instead of dying on `fixed_delta_seconds is None` (re-apply settings / fall back to the measured delta).
