### Source-derived checks (not taken on trust)

- Nesting matches the width constants: the algo hint is added straight to `AgentBox`
  (`STestPlatformUI.cpp:1027-1033`) → 384−2×10 = 364 u correct; the summary hint is inside
  `Card()` (`:1170-1194`), which nests two 12 u borders (`:252-265`) → 340 u correct.
  `WrappedText()` has exactly two call sites; `Text()` is untouched.
- `WrapTextAt` + `AutoWrapText` is the right pair: `FSlateTextBlockLayout::CalculateWrappingWidth()`
  (`Engine/.../SlateTextBlockLayout.cpp:397-408`) takes `min(WrapTextAt, CachedSize.X)` when
  auto-wrap is on, and `SScrollBox::ConstructVerticalLayout()` (`SScrollBox.cpp:341-395`) puts the
  bar in an `AutoWidth` slot beside the `FillWidth(1)` content — so a future scrollbar shrinks the
  allotment instead of covering the text. The comment in the code is accurate.
- Chip text and dot cannot diverge: both are computed from one `State` string in the same
  `if (ServerChipText.IsValid())` block (`:1510-1530`), and that string is the only place
  `ServerChipText`/`ServerDot` are written. `grep 已连接|未连接|未知` finds no other surface.
- Refresh really is live: `未连接` (backend probing 2005) → backend restarted on 2000 →
  `已连接` in the **same** editor PID within 22 s, no restart; then backend stopped →
  `未知` within 16 s. `/health` returned `connected:false`, then `connected:true`, then
  refused — the three states are real, occur, and are distinguishable in the log and on screen.
- Default state cannot lie: `bCarlaKnown`/`bCarlaConnected` start false and `HasCarlaState()`
  is false, so before any `/health` answer the chip reads `未知`, never `已连接`
  (`TestPlatformApi.cpp:375-398`, `STestPlatformUI.cpp:1516-1518`).

## Problems found (adversarial)

- **P1 (non-blocking, pre-existing): the chip's address is hardcoded to `127.0.0.1 : 2000`,
  while the state now comes from whatever host/port the backend probes.**
  Repro: start the backend with `CARLA_PORT=2005`, run the panel in game mode (its own CARLA
  RPC server is on 2000 — confirmed: `Get-NetTCPConnection` shows 2000/2001/2002 owned by the
  editor PID while the chip says `未连接`). Observed: `服务器 127.0.0.1 : 2000 · 未连接` although
  2000 was alive; `/health` reported `"host":"127.0.0.1","port":2005`. The *state* is honest,
  the *address label* is not, and `/health` already carries the real `host`/`port` the label
  could use. This string predates both commits (old code used the same hardcoded address), so
  it is not a regression — but it is the one way this line can still mislead.
- **P2 (non-blocking, process): the working tree is not clean.** 18 new evidence PNGs under
  `Source/TestPlatform/Platform/ui/` (`panel-hint-*`, `panel-fixed-*`, `panel-dot-*`) are
  untracked although that directory tracks 44 earlier PNGs — by this repo's own convention
  the evidence should have been committed with the change.
- **P3 (non-blocking, style/legibility): `未连接` uses `ColMuted (196,206,215)` and `未知`
  uses `ColDim (168,180,191)`** — two greys 24–28 sRGB steps apart. Both are clearly not the
  teal "healthy" state, but telling "disconnected" from "no answer yet" by dot colour alone is
  a squint; the words do carry the distinction.
- **P4 (unverified risk): a CARLA probe that times out during a blocking map load would now
  read `未连接`.** `/health` probes with a 1 s timeout and the panel now asks every 5 s, so if
  the world is wedged 30–90 s while a heavy map loads (the panel itself documents that case),
  the chip could claim `未连接` while CARLA is fine. That is a false negative, not the original
  false "healthy"; I could not reproduce it inside one editor run.
- **P5 (non-blocking): no automated test** covers this UI; the verdict rests on a compile plus
  measured pixels.
