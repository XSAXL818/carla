## Problems found (adversarial)

### D1 — BLOCKING. The watchdog is disarmed by *any* client on the RPC port, so a killed backend no longer
### guarantees recovery: the editor can stay frozen forever, and no value of `carla.SyncCueTimeout` helps.
Reproduction (verbatim, ~2 minutes; needs the editor built from this tree and any preview session in sync mode):
1. Start the backend and get a preview session: `POST /sessions/preview_map {"map":"Town10HD"}`; wait for
   `GET /sessions/current` → `state=preview, sync_mode=true`.
2. Start a second CARLA client that connects and then sends nothing:
   `python -c "import carla,time; c=carla.Client('127.0.0.1',2000); c.set_timeout(20); c.get_world(); time.sleep(300)"`.
   (A monitoring script, a second tool, a notebook holding a world handle — any of them.)
3. Kill the backend: `Stop-Process -Id <run.py pid> -Force`.
4. Sample the editor window: `SendMessageTimeout(hwnd, WM_NULL, …, SMTO_BLOCK|SMTO_ABORTIFHUNG, 800, …)`.
   **Observed**: `Responding=False` for the whole observation; at t=60 s the log says
   `Warning: No tick cue for 60 s in synchronous mode, but a client is still connected to RPC port 2000: waiting
   for it …`; at t=78 s the editor is still unresponsive, there is **no** `Synchronous mode lost` Error, and no
   fallback — the wait is unbounded (`CarlaEngine.cpp:1072-1084`: on `Present` it only logs once, then continues
   the `do…while`, and nothing else can end the wait).
   Killing the *idle* client at t=97 s produced `Error: Synchronous mode lost: no tick cue for 97 s and no client
   is connected to the RPC port any more` and the editor became responsive 0.5 s later — i.e. the only thing that
   released it was every client disappearing.
Why it fails the task: requirement 3 says "with the backend killed mid-preview, the editor must still recover".
Here the backend *is* killed mid-preview and the editor does not recover; `carla.SyncCueTimeout=600` changes
nothing and `0` also never returns. The gating signal (`GetExtendedTcpTable` ESTABLISHED on the RPC port,
`CarlaEngine.cpp:136-166`) answers "is *anybody* connected", not "is the client that stopped sending tick cues
still there", and the previous 15 s watchdog always recovered — so this is a regression of the property that
made the watchdog exist. Multi-client is normal for CARLA (my own preview run held 3 ESTABLISHED rows on port
2000), and the committed `CHANGELOG.md` bullet ("closing the backend window while a preview session is in
synchronous mode no longer freezes the editor") and `architecture.md` make the guarantee without this condition.
Possible narrow remedies (implementation's call): remember/verify the RPC session that sent the last
synchronous settings + tick cue instead of counting connections; or add a hard cap / an escape hatch
(e.g. a `carla.ForceAsync` console command, or a "waiting for a connected client" state the panel can abort),
so a connected-but-dead clock cannot wedge the editor indefinitely.

### D2 — Doc over-claim (follows from D1).
`CHANGELOG.md` (the new bullet) and `architecture.md` disclose the non-Windows (`Unknown`) trade-off, but not
that *any* connected client disables the fallback. A user reading "only fires once no client is connected to the
RPC port any more" would not expect a second idle client to make the editor unrecoverable.

### D3 — Minor, design note: while any client is connected the timeout is inert.
`carla.SyncCueTimeout` only decides *how long after the last connection disappears* to give up; raising it does
nothing for a connected client that never sends a cue (a hung agent, a deadlocked script, a debugger pause left
overnight). The cvar help text and `architecture.md` say this, so it is documented, but it means the knob does not
do what "configurable timeout with a way to disable it" suggests for the connected case.

### D4 — Minor: include-order noise added to `CarlaEngine.cpp`.
The new block (`CarlaEngine.cpp:59-70`) produces in the compile of that TU:
`You have included windows.h before MinWindows.h …` and `warning C4005: "NOMINMAX": 宏重定义`. Non-blocking and
warning-only; I could not attribute it to this commit with certainty (no pre-commit build log on disk), so it is
recorded as an observation, not a failure.
